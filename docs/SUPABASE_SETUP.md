# Подготовка Supabase для CRM «Поток»

Дата проверки документации: 22 сентября 2026 года.

Файлы 001–004 прошли локальную проверку в PGlite (PostgreSQL в WASM) с эмуляцией схемы Auth и ролей Supabase: создание таблиц, CRUD владельца, запреты чужого/анонимного доступа, составные связи, каскадное удаление тестового владельца и откат тестовых записей. К облачному проекту эта проверка не подключалась; выполните 004 также в своём Supabase.

Это инструкция для нового облачного проекта Supabase и личной CRM на `https://proaksenov.ru`. После её выполнения база и учётная запись будут подготовлены. Подключение интерфейса требует следующего изменения кода: сейчас приложение продолжает использовать localStorage.

Для базы и входа переходить на SSR не требуется: браузер может обращаться к Supabase через публичный ключ, а Supabase Auth и Row Level Security (RLS) ограничивают доступ владельцем записей. Серверную интеграцию с Авито будем подключать отдельно. Домен CRM остаётся на Timeweb; менять DNS на Supabase не нужно.

## 1. Создать проект

Откройте [панель Supabase](https://supabase.com/dashboard), войдите и создайте организацию, если её ещё нет. Для проверки можно начать с Free: у него есть лимиты, нет автоматических резервных копий, неактивные проекты приостанавливаются. Перед рабочим использованием пересмотрите тариф и резервное копирование по [актуальным условиям](https://supabase.com/pricing).

Создайте New project:

- название: `proaksenov-crm`;
- пароль базы данных: сгенерируйте и сохраните у себя в менеджере паролей;
- регион: доступный регион, подходящий для размещения ваших данных и близкий к пользователям/будущему серверу;
- дождитесь завершения создания проекта.

Пароль PostgreSQL отличается от пароля входа в CRM и от API-ключей.

## 2. Настроить вход владельца

В Authentication → Sign In / Providers оставьте включённым Email. Для первого подключения используем вход по email и паролю.

В Authentication → Users создайте своего пользователя через Add user → Create new user. Укажите свой email и отдельный пароль для CRM. Для собственной учётной записи, созданной администратором, выберите Auto Confirm User, если этот переключатель показан. Используйте именно создание пользователя с паролем: приглашение по email потребует ещё не реализованной обработки ссылки в приложении.

После создания отключите **Allow new users to sign up**, поскольку CRM пока только для вас. **Allow anonymous sign-ins** оставьте выключенным. Не отключайте подтверждение email глобально ради создания одного пользователя.

Управление пользователями Supabase Dashboard и пользователями Authentication — разные вещи. Для входа в CRM нужен пользователь в Authentication → Users.

Источники: [настройки Auth](https://supabase.com/docs/guides/auth/general-configuration), [пользователи](https://supabase.com/docs/guides/auth/managing-user-data).

## 3. Указать адрес CRM в Supabase Auth

В Authentication → URL Configuration:

- Site URL: `https://proaksenov.ru`;
- Redirect URLs: `https://proaksenov.ru/` и для локальной разработки `http://127.0.0.1:3000/`.

Локальный сервер проекта запускается на `127.0.0.1`, поэтому используйте именно этот адрес. Если будете открывать его через `localhost`, добавьте отдельно `http://localhost:3000/`.

Вход по паролю не использует переход по письму. Эти настройки задают разрешённые адреса; сами по себе они не реализуют подтверждение email или сброс пароля. Для этих сценариев обработку добавим вместе с экраном входа.

`https://proaksenov.ru/api/avito/callback` — отдельный callback Авито. Он не является настройкой входа Supabase и пока не реализован.

Источник: [Redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls).

## 4. Создать таблицы из SQL-файлов

В SQL Editor открывайте новый запрос, вставляйте ПОЛНОЕ содержимое одного файла и нажимайте Run. Выполняйте строго по порядку и проверяйте отсутствие ошибок перед следующим файлом:

1. [001_create_products_table.sql](001_create_products_table.sql) — товары, цены, этапы, показатели, дата продажи.
2. [002_create_buyers_table.sql](002_create_buyers_table.sql) — покупатели, контактные данные, заметки, связь с товаром.
3. [003_create_messages_table.sql](003_create_messages_table.sql) — история сообщений покупателей.
4. [004_verify_crm_rls.sql](004_verify_crm_rls.sql) — проверка доступа и связей с временными данными, которые откатываются.

Файлы 001–003 рассчитаны на НОВЫЙ проект и однократное применение. Если уже есть таблицы с такими именами, сначала нужно сравнить схемы. Повторный запуск намеренно выдаёт ошибку, а не скрывает несовпадение структуры.

Таблицы и их RLS создаются одной транзакцией в каждом файле. Не нужно включать публичный доступ через дополнительные шаблоны политик. Ключ API сам по себе не даёт доступа к данным CRM: нужен вход пользователя, затем RLS пропускает только его строки.

В Table Editor → public появятся `products`, `buyers`, `messages`. Пустые таблицы на этом этапе нормальны. Демоданные автоматически не переносятся. Данные пользователя CRM хранятся в управляемой Supabase таблице `auth.users`; отдельная таблица паролей не создаётся.

Проверка 004 рассчитана на новый проект без собственных триггеров на `auth.users`. Она временно создаёт двух технических пользователей внутри транзакции и эмулирует их роли/ID на уровне PostgreSQL. Это проверка RLS и внешних ключей, а не реальная авторизация через HTTP. При успешном запуске запрос перед откатом возвращает `PASS: owner CRUD, cross-owner isolation, composite foreign keys and anonymous denial`; после финального ROLLBACK редактор может показывать только `Success. No rows returned`. Важно выполнение всего файла без ошибок. После будущего подключения интерфейса отдельно проверим вход и запросы через клиент Supabase.

Источник принципов доступа: [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security).

## 5. Получить параметры подключения

В проекте нажмите **Connect** и выберите параметры для JavaScript/Next.js, либо откройте **Settings → API Keys**. Нужны:

- Project URL вида `https://<project-ref>.supabase.co`;
- Publishable key вида `sb_publishable_...`.

Это параметры браузерного клиента. Secret key (`sb_secret_...`), устаревший `service_role`, пароль базы и ключи Авито для данного этапа не нужны. Они не должны попадать в `NEXT_PUBLIC_*`.

Источник: [API keys](https://supabase.com/docs/guides/getting-started/api-keys).

## 6. Подготовить окружение проекта и Timeweb

Локально скопируйте `.env.example` в `.env.local`, замените два примера на свои значения. `.env.local` уже исключён из Git. `.env.example` содержит только образцы.

В Timeweb App Platform → ваше приложение → настройки переменных добавьте эти же две переменные, доступные при сборке:

```env
NEXT_PUBLIC_SUPABASE_URL=https://your-project.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

Текущую `NEXT_OUTPUT=export` оставьте: база через браузер не требует изменения статического деплоя. При подключении Supabase в коде потребуется новая сборка, потому что Next.js включает `NEXT_PUBLIC_*` в браузерный код во время сборки. Одно добавление переменных ещё не изменит поведение текущего приложения.

Источники: [Next.js — переменные окружения](https://nextjs.org/docs/app/guides/environment-variables), [переменные Timeweb](https://timeweb.cloud/docs/apps/variables).

## 7. Следующий этап — изменение приложения

После настройки нужны только Project URL, Publishable key и подтверждение успешного выполнения 001–004. Пароль CRM, пароль БД и серверный secret key передавать в переписку не требуется.

В код предстоит добавить `@supabase/supabase-js`, экран входа/выхода, загрузку только данных вошедшего пользователя, операции сохранения и сообщения об ошибках. Это отдельное изменение; в этом наборе файлов оно ещё не сделано. Демоданные нельзя автоматически записывать в базу при каждом входе.

Перед переносом существующих записей потребуется адаптер:

| Текущая модель | SQL | Правило |
| --- | --- | --- |
| `id` вида `product-chair` | `id uuid` | Создать новые UUID и согласованно перенести связи покупателей/сообщений |
| Нет владельца | `owner_id` | UUID вошедшего пользователя Supabase; значение по умолчанию `auth.uid()` |
| `createdAt`, `soldAt` | `created_at`, `sold_at` | ISO-даты; stage=sold и sold_at изменять одним запросом |
| `productId: ""` | `product_id: null` | Пустую связь преобразовать в null |
| `buyerId` | `buyer_id` | Ссылка на UUID покупателя того же владельца |
| `image` с base64/локальным URL | `image_path` | Фото перенести в Storage отдельно; до этого использовать заглушку |

`numeric` для цены округляет сумму до копеек. Таблицы не хранят ключи/токены Авито; сообщения из базы пока не являются отправкой в Авито. Публичный Storage bucket и Realtime этим этапом не создаются.

Удаление товара с привязанными покупателями запрещено: сначала отвяжите покупателей. Покупателя с сообщениями также нельзя удалить без отдельного решения по его истории. Удаление пользователя через администрирование Supabase удаляет его CRM-данные каскадом.
