# Переписка Авито: webhook и Realtime

Контракт сверён с предоставленной пользователем спецификацией «Мессенджер»,
версия 1 (`swagger (1).json`). Документация:
https://developers.avito.ru/api-catalog/messenger/documentation

## Что реализовано

- «Сообщения → Авито — реальные сообщения»: выбор собственного аккаунта,
  список диалогов с именем собеседника и объявлением, история, текстовый ответ.
- Новые сообщения приходят через `avito-webhook`, сохраняются в Supabase и
  доставляются в браузер через Realtime. Постоянный опрос Авито отключён.
- API-история сверяется при открытии чата, возвращении на вкладку и восстановлении
  Realtime. Повторные сверки ограничены паузой 30 секунд, без периодического таймера.
  Ручное обновление остаётся доступным. Отправка ответа не запускает лишнюю сверку.
- После подключения Realtime читаются 200 последних сохранённых сообщений,
  чтобы закрыть промежуток между загрузкой страницы и подключением канала.
  При недоступности API показывается сохранённая история с явным предупреждением
  о возможной неполноте. Старые сообщения сохраняются по мере открытия страниц;
  автоматического полного импорта старой переписки нет.
- Дубли webhook/API/отправки объединяются по владельцу, аккаунту, чату и ID.
  Запоздавшая история не восстанавливает удалённый текст или непрочитанный статус.
  Новый диалог без метаданных временно называется «Собеседник Авито»; имя и название
  объявления появляются после сверки списка с API.
- Страницы по 50 записей, offset до 1000 (предел спецификации).
  Новые диалоги и сообщения смотрите на первой странице; старые доступны
  отдельными страницами. Это не выгрузка всей истории аккаунта.
- Прочтение открытого диалога отмечается в Авито после загрузки последней
  страницы сообщений, если есть непрочитанные входящие. Используется `is_read`
  из API, не `read` (время прочтения собеседником). Фоновое чтение списка чатов
  и просмотр старых страниц не отмечают их прочитанными.
- Успешная отметка запоминается на время открытого чата: обновление истории
  не повторяет её для тех же сообщений. Запросы прочтения не пересекаются.
  При отказе видны причина и HTTP-статус, есть отдельная кнопка повтора.
  Переписка и черновик остаются на месте; повтор не отправляет сообщения.
  Та же ошибка не повторяет POST при каждом автообновлении. Если API вернул `is_read: true`,
  устаревшее предупреждение очищается. Ошибка `invalid_action` отдельно указывает
  на необходимость обновить опубликованную Edge Function, а не тариф.
- Ответы до 1000 символов. Вложения обозначаются текстом; отправка фото,
  проигрывание голоса и удаление сообщений из интерфейса не реализованы.
- При неопределённом результате отправки текст остаётся в поле. Нет
  автоматического повтора: сначала проверьте переписку, затем явно разрешите
  повтор. API не предоставляет в этой спецификации ключ идемпотентности;
  гарантия «ровно один раз» при ручном повторе после таймаута невозможна.
- «Черновики CRM» и демо остаются отдельными, ничего не отправляют в Авито.

## Публикация

1. Для аккаунта должен быть доступен Messenger API. По предоставленной
   спецификации: Товары/Работа — «Максимальный», Услуги — «Расширенный» или
   «Максимальный». Для компании нужны ключи основного аккаунта, не сотрудника.
2. В SQL Editor выполните целиком [009_create_avito_messenger.sql](009_create_avito_messenger.sql),
   один раз. Затем [010_verify_avito_messenger.sql](010_verify_avito_messenger.sql):
   тестовые записи создаются в транзакции и откатываются через ROLLBACK.
3. В Edge Functions → Secrets добавьте `AVITO_WEBHOOK_SECRET`: 32 случайных байта
   в виде **64 шестнадцатеричных символов**. Генерация локально:

   ```powershell
   node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
   ```

   Не присылайте значение в чат и не добавляйте его в `NEXT_PUBLIC_*`, Git или Timeweb.
   Используются существующие серверные `AVITO_CLIENT_ID`, `AVITO_CLIENT_SECRET`,
   `AVITO_CRM_OWNER_ID`, `AVITO_ALLOWED_ORIGINS`.
   `SUPABASE_SERVICE_ROLE_KEY` и `SUPABASE_URL` доступны размещённым функциям
   Supabase автоматически. Код также понимает новый `SUPABASE_SECRET_KEYS.default`.
   Эти ключи в браузер передавать нельзя.
    Для подключения применяется OAuth Authorization Code. Перед первым подключением
    выполните [011_create_avito_oauth.sql](011_create_avito_oauth.sql) после SQL 009.
    Единственный Redirect URL приложения Авито должен точно совпадать с
    `https://proaksenov.ru/api/avito/callback`; локальный запуск использует этот
    production callback и после обмена кода возвращается на `127.0.0.1`. Если `/token` возвращает
    `unauthorized_client` уже при обмене кода, проверьте Client ID, Client Secret
    и Redirect URL в настройках приложения Авито.
4. Выполните `npm.cmd run avito:bundle`. Сначала опубликуйте новую функцию
   **avito-webhook** из `artifacts/avito-webhook-function/index.ts`.
   Отключите проверку JWT **только для avito-webhook**: Авито не имеет сеанса CRM.
   Защита секретным адресом остаётся внутри обработчика. Затем обновите функцию
   **avito** из `artifacts/avito-function/index.ts`; её проверку JWT оставьте включённой.
   При использовании CLI применяются настройки `supabase/config.toml`.
5. Соберите и опубликуйте фронтенд из нужной ветки (`dev` для проверки).
   Сборка bundle сама по себе ничего не публикует.
6. Войдите владельцем CRM, откройте «Сообщения», выберите аккаунт и нажмите
   **«Подключить webhook»**. Это однократная регистрация, не кнопка загрузки сообщений.
   Сервер определяет профиль Авито, проверяет приёмник и регистрирует URL.
   Чужие подписки не удаляются; повторное подключение не дублирует этот URL.
7. Отправьте согласованное тестовое сообщение из другого аккаунта Авито.
   Проверьте появление без кнопки обновления, ответ, перезагрузку страницы и
   восстановление после разрыва сети. Повторная проверка регистрации показывает
   также время последнего принятого события.

Переписка хранится отдельно от таблицы черновиков `messages`. На клиент не
передаются ключи, токены Авито или секретный callback URL. ID аккаунта определяется
сервером по авторизованному профилю. Webhook не обходит HTTP 402/403 и не заменяет chatRead.
Тексты переписки не пишутся в логи и localStorage. Закрытие страницы очищает
несохранённый текст ответа. Webhook сохраняет сообщения и при закрытой CRM;
браузерные push-уведомления не реализованы. Автоматического срока удаления копий
пока нет; удаление пользователя Supabase удаляет его записи каскадно.
Счётчики на главной CRM относятся к локальным данным, не к переписке Авито.

## Схема и защита

SQL 009 описывает `avito_messenger_accounts` (подтверждённая связь владельца и
аккаунта, статус регистрации, время события) и `avito_messenger_messages`
(нормализованные сообщения). Браузер имеет только SELECT своих данных через RLS.
Функции записи `avito_cache_messages` и `avito_mark_cached_read` доступны только
`service_role`; `avito_cached_chats` читает с правами пользователя и соблюдает RLS.
В `supabase_realtime` добавлена только таблица сообщений этой интеграции.

В спецификации Авито не описан заголовок подписи webhook. Поэтому используется
секретный URL с HMAC-токеном, привязанным к владельцу, ключу подключения, ID Авито
и Client ID. `payload.value.user_id` проверяется против URL и серверной связи в БД.
Это защита секретным URL, **не подпись тела от Авито**: владелец полного URL сможет
подделывать события этого аккаунта. Не публикуйте URL, логи запросов или список
подписок. При утечке смените секрет, переподключите webhook и удалите только его
старую подписку. Остальные приложения обработчик не отключает.

Приёмник принимает POST с телом до 64 КиБ, не вызывает API Авито и отвечает 200
только после транзакции БД. При проблеме сохранения отвечает 503. Документация
Авито требует ответ за 2 секунды: чтение тела ограничено 350 мс, запрос БД — 1500 мс.
Реальное время с холодным запуском функции проверяется после публикации.
Получение webhook в фоне не помечает чат прочитанным.

## Методы и проверки

- GET `/messenger/v2/accounts/{user_id}/chats` — объект `{ chats: [...] }`.
- GET `/messenger/v3/accounts/{user_id}/chats/{chat_id}/messages/` — массив,
  **не** объект `{ messages: [...] }`.
- POST `/messenger/v1/accounts/{user_id}/chats/{chat_id}/messages` —
  `{ "type": "text", "message": { "text": "…" } }`, ответ содержит ID сообщения.
- POST `/messenger/v1/accounts/{user_id}/chats/{chat_id}/read` — отметка прочтения.
  Запрос без тела и без `Content-Type`; после успеха Edge Function возвращает
  `{ "read": true }`. Клиент проверяет это подтверждение.
- POST `/messenger/v1/subscriptions` — проверка существующих подписок.
- POST `/messenger/v3/webhook` с `{ "url": "…" }` — регистрация.

`npm.cmd test` проверяет контракт, валидацию и обработку webhook на моках;
SQL 009 и 010 выполняются в настоящем PostgreSQL через PGlite без облачной БД.
`npm.cmd run test:e2e -- tests/messenger.spec.ts` проверяет браузерные сценарии
с настоящим SDK Supabase, подменёнными Auth/API/WebSocket, без отправки покупателям.
Реальную доступность API и доставку нужно отдельно проверить после публикации.

### Результат локальной проверки 30.09.2026

- 53 автоматических теста прошли, включая SQL 009–010 в PostgreSQL/PGlite.
- Все 10 браузерных сценариев мессенджера прошли: Realtime, отсутствие периодического опроса,
  восстановление сети, сохранённая история, удалённые сообщения, изоляция аккаунтов и отметки прочтения.
  После выполнения сценариев Playwright завис на завершении dev-сервера в Windows; процесс остановлен вручную.
- Production-сборка с `NEXT_OUTPUT=export` и проверкой TypeScript прошла.
  Обе Dashboard-сборки созданы и проверены на синтаксис и отсутствие внешних импортов.
- Облачные SQL/функции и регистрация в реальном Авито этой проверкой не изменялись.
- `npm audit` отдельно выявил критическую уязвимость установленного Next.js 16.3.5
  (`GHSA-vcvr-r3jv-pc5j`, исправление 16.3.6). Обновление Next.js не входит в эту правку;
