# Переписка Авито

Контракт сверён с предоставленной пользователем спецификацией «Мессенджер»,
версия 1 (`swagger (1).json`). Документация:
https://developers.avito.ru/api-catalog/messenger/documentation

## Что реализовано

- «Сообщения → Авито — реальные сообщения»: выбор собственного аккаунта,
  список диалогов с именем собеседника и объявлением, история, текстовый ответ.
- Автообновление раз в 2 минуты, пока раздел открыт и вкладка видима.
  При ошибке следующая автоматическая попытка — через 5 минут. Интервал
  отсчитывается от завершения запроса отдельно для списка диалогов и истории.
  Возврат на вкладку и завершение отправки ответа не сбрасывают интервал.
  После долгого отсутствия выполняется одно обновление, без накопленных запросов.
  Новый чат, аккаунт или страница загружаются сразу. Существующие кнопки
  позволяют при необходимости явно обновить данные раньше срока.
- Страницы по 50 записей, offset до 1000 (предел спецификации).
  Новые диалоги и сообщения смотрите на первой странице; старые доступны
  отдельными страницами. Это не выгрузка всей истории аккаунта.
- Прочтение открытого диалога отмечается в Авито после загрузки последней
  страницы сообщений, если есть непрочитанные входящие. Используется `is_read`
  из API, не `read` (время прочтения собеседником). Фоновое чтение списка чатов
  и просмотр старых страниц не отмечают их прочитанными.
- Успешная отметка запоминается на время открытого чата: обновление истории
  не повторяет её для тех же сообщений. Запросы прочтения не пересекаются.
  При отказе видны причина и HTTP-статус, есть отдельная кнопка повтора.
  Переписка и черновик остаются на месте; повтор не отправляет сообщения.
  Та же ошибка не повторяет POST при каждом автообновлении. Если API вернул `is_read: true`,
  устаревшее предупреждение очищается. Ошибка `invalid_action` отдельно указывает
  на необходимость обновить опубликованную Edge Function, а не тариф.
- Ответы до 1000 символов. Вложения обозначаются текстом; отправка фото,
  проигрывание голоса, удаление сообщений и webhooks не реализованы.
- При неопределённом результате отправки текст остаётся в поле. Нет
  автоматического повтора: сначала проверьте переписку, затем явно разрешите
  повтор. API не предоставляет в этой спецификации ключ идемпотентности;
  гарантия «ровно один раз» при ручном повторе после таймаута невозможна.
- «Черновики CRM» и демо остаются отдельными, ничего не отправляют в Авито.

## Публикация

1. Для аккаунта должен быть доступен Messenger API. По предоставленной
   спецификации: Товары/Работа — «Максимальный», Услуги — «Расширенный» или
   «Максимальный». Для компании нужны ключи основного аккаунта, не сотрудника.
2. Используются существующие серверные `AVITO_CLIENT_ID`, `AVITO_CLIENT_SECRET`,
   `AVITO_CRM_OWNER_ID`, `AVITO_ALLOWED_ORIGINS`. Новых секретов не требуется.
   Для своего аккаунта применяется `client_credentials`; OAuth сторонних
   пользователей в этой CRM пока не реализован.
3. Выполните `npm.cmd run avito:bundle`. Опубликуйте содержимое
   `artifacts/avito-function/index.ts` в существующей Supabase Edge Function
   **avito**, как описано в [AVITO_SETUP.md](AVITO_SETUP.md).
4. Соберите и опубликуйте фронтенд из нужной ветки (`dev` для проверки).
   Сборка bundle сама по себе ничего не публикует.
5. Войдите владельцем CRM, откройте «Сообщения», выберите аккаунт и диалог.
   Проверьте входящее сообщение и отправьте согласованный тестовый ответ.

Новые SQL-файлы не нужны: переписка читается из Авито через защищённую функцию,
без копирования в таблицу черновиков `messages`. На клиент не передаются ключи
или токены Авито. ID аккаунта определяется сервером по авторизованному профилю.
Тексты переписки не пишутся в логи и localStorage. Закрытие страницы очищает
несохранённый текст ответа. Без открытого раздела обновления и уведомлений нет.
Счётчики на главной CRM относятся к локальным данным, не к переписке Авито.

## Методы и проверки

- GET `/messenger/v2/accounts/{user_id}/chats` — объект `{ chats: [...] }`.
- GET `/messenger/v3/accounts/{user_id}/chats/{chat_id}/messages/` — массив,
  **не** объект `{ messages: [...] }`.
- POST `/messenger/v1/accounts/{user_id}/chats/{chat_id}/messages` —
  `{ "type": "text", "message": { "text": "…" } }`, ответ содержит ID сообщения.
- POST `/messenger/v1/accounts/{user_id}/chats/{chat_id}/read` — отметка прочтения.
  Запрос без тела и без `Content-Type`; после успеха Edge Function возвращает
  `{ "read": true }`. Клиент проверяет это подтверждение.

`npm.cmd test` проверяет контракт, валидацию и изоляцию владельцев на моках.
`npm.cmd run test:e2e -- tests/messenger.spec.ts` проверяет браузерные сценарии
с подменёнными Auth/API, без реальной отправки покупателям.
Реальную доступность API и доставку нужно отдельно проверить после публикации.
